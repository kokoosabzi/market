# مشخصات مرحلهٔ S2 — صندوق فروش سریع (POS)

## هدف
تبدیل ثبت فروش از فرم عمومی سند به فضای کاری سریع و متمرکز فروش، بدون تغییر در قواعد محاسباتی، شماره‌گذاری، نهایی‌سازی یا گردش موجودی موجود.

## تصمیم‌های تثبیت‌شده
- فروش جدید از صفحهٔ اصلی فروش آغاز می‌شود.
- خریدار و یادداشت اختیاری هستند؛ فروش حضوری بدون نام خریدار مجاز است.
- تاریخ سند در این مرحله از کنترل تاریخ بومی موجود استفاده می‌کند و پیش‌نمایش شمسی حفظ می‌شود.
- مبالغ پایگاه داده ریال صحیح هستند؛ واحد نمایشی تابع تنظیم فعلی ریال/تومان است.
- پرداخت و صندوق دریافت وجه در دامنهٔ Market نیستند.
- فاکتور/چاپ در S3 انجام می‌شود؛ S2 باید شناسه و دادهٔ سند را برای آن مرحله بدون تولید فاکتور مستقل حفظ کند.

## تجربهٔ کاربری POS
1. نوار بالایی: شمارهٔ موقت/وضعیت «فروش جدید»، تاریخ، ورودی اختیاری خریدار.
2. جست‌وجوی کالا: جست‌وجو بر اساس کد یا نام؛ نتایج فقط کالاهای فعال؛ انتخاب با صفحه‌کلید و ماوس؛ نمایش کد، نام، واحد، قیمت فروش و موجودی جاری.
3. سبد فروش: افزودن کالا، افزایش تعداد با افزودن دوبارهٔ همان کالا، امکان ویرایش مقدار/قیمت/تخفیف و حذف ردیف؛ هر ردیف واحد و جمع قابل مشاهده داشته باشد.
4. خلاصهٔ مبالغ: ناخالص، تخفیف، مالیات طبق تنظیم موجود، مبلغ نهایی؛ محاسبات قطعی سمت main و با تابع مالی موجود انجام می‌شود.
5. نوار عملیات: «ذخیره پیش‌نویس»، «صدور فروش» و «انصراف». صدور فروش، تأیید نهایی و سپس همان API موجود `documents:finalize` را فراخوانی می‌کند.
6. پس از موفقیت: پیام شمارهٔ سند قطعی و دکمهٔ بازگشت به فهرست فروش. چاپ فاکتور تا S3 ارائه نمی‌شود و UI نباید دکمهٔ چاپ غیرعملی نشان دهد.

## قواعد داده و تراکنش
- جست‌وجوی کالا از API محدود preload و IPC فعلی استفاده می‌کند؛ renderer به SQLite یا Node دسترسی مستقیم ندارد.
- موجودی صرفاً برای اطلاع نمایش داده می‌شود؛ رفتار فعلی مجاز بودن موجودی منفی حفظ می‌شود و فروش به‌علت موجودی ناکافی رد نمی‌شود.
- یکسان بودن کالا در سبد با productId تشخیص داده می‌شود؛ افزودن دوباره، مقدار همان ردیف را افزایش می‌دهد.
- برای کالاهای شمارشی (عدد/بسته/سرویس) مقدار کسری مجاز نیست؛ برای واحدهای وزنی/طولی/حجمی دقت سه رقم اعشار حفظ می‌شود.
- تخفیف ثابت/درصد، سقف تخفیف، مالیات و گردکردن فقط با منطق سمت main مرجع نهایی است؛ جمع renderer صرفاً پیش‌نمایش است.
- پیش‌نویس از API موجود ذخیره می‌شود؛ صدور مجدد سند قطعی نباید گردش موجودی تکراری ایجاد کند.
- تغییر قیمت در POS فقط روی همان سند/ردیف اعمال می‌شود و قیمت پیش‌فرض از قیمت فروش جاری کالا می‌آید.
- حذف یا غیرفعال‌سازی کالا پس از ایجاد پیش‌نویس باید مطابق اعتبارسنجی فعلی سمت main مدیریت شود؛ خطا با پیام قابل فهم نمایش داده شود.

## قرارداد فنی پیشنهادی
- S2a: افزودن API جست‌وجوی سریع با query محدود و بازگرداندن موجودی جاری؛ اگر API فهرست کالاها برای این منظور کافی باشد، از همان API استفاده و از IPC تکراری اجتناب شود.
- S2b: ساخت کامپوننت/بخش POS مجزا در renderer؛ فرم خرید عمومی دست‌نخورده باقی بماند.
- S2c: اتصال سبد به `documents:save-draft` و `documents:finalize` موجود.
- S2d: نمایش خطاهای اعتبارسنجی، حالت درحال‌ذخیره، جلوگیری از submit دوباره و پاک‌سازی state فقط پس از پاسخ موفق.
- S2e: آزمون واحد محاسبهٔ نمایشی و آزمون‌های IPC/main برای مقدار، تخفیف، مالیات، موجودی منفی، خریدار خالی، تکرار کالا و نهایی‌سازی دوباره.

## معیارهای پذیرش
- جست‌وجوی کالا با کد و نام پاسخ روشن و انتخاب سریع داشته باشد.
- افزودن چندبارهٔ یک کالا به افزایش مقدار همان ردیف منجر شود.
- جمع سبد در تغییر مقدار/قیمت/تخفیف به‌روز شود و با خروجی سمت main برابر باشد.
- فروش بدون نام خریدار قابل ذخیره و نهایی‌سازی باشد.
- پیش‌نویس پس از بازگشایی همان اقلام و مقادیر را بازیابی کند.
- فروش قطعی دقیقاً یک شماره و یک گردش موجودی ایجاد کند.
- خطای عملیات، اطلاعات سبد را پاک نکند.
- خرید، برگشت، گزارش و پشتیبان‌گیری بدون تغییر رفتار باقی بمانند.
- آزمون‌ها و smoke روی Windows اجرا و نتیجه ثبت شود.

## خارج از محدوده

- ثبت پرداخت، دریافت وجه، صندوق و ماندهٔ مشتری.
- حساب اشخاص و اعتبار/بدهی.
- تغییر سیاست موجودی منفی یا الگوریتم بهای تمام‌شده.
