# طراحی فنی فروش‌محور و فاکتور Market

## وضعیت و تصمیم‌های تأییدشده
- این طرح برای شاخهٔ `feature/sales-first-invoicing` و بر پایهٔ `main` نوشته شده است.
- منوی فروش، نقطهٔ ورود اصلی تجربهٔ کاربری است؛ «نمای کلی» از نقش صفحهٔ آغازین غالب خارج می‌شود.
- مشخصات خریدار اختیاری است؛ فروش بدون نام خریدار معتبر است.
- هنگام چاپ، کاربر بین فاکتور A4 و فیش حرارتی ۸۰ میلی‌متری انتخاب می‌کند.
- پرداخت، تسویه، صندوق و دفتر اشخاص در این محدوده نیستند.
- زبان رابط و فاکتور فارسی و جهت RTL باقی می‌ماند.

## ممیزی وضع موجود
- جدول `documents` هم‌اکنون نوع سند، شماره، تاریخ، وضعیت، نام طرف معامله، یادداشت و جمع‌های مالی را نگهداری می‌کند.
- جدول `document_items` ردیف کالا، مقدار، قیمت واحد، تخفیف، مالیات، مبلغ نهایی و snapshot بهای تمام‌شده را نگهداری می‌کند.
- `documents:finalize` نهایی‌سازی را در تراکنش SQLite انجام می‌دهد، شمارهٔ یکتا از الگوی `SAL-########` می‌سازد و گردش موجودی را ثبت می‌کند.
- `documents:get` اطلاعات سند و ردیف‌ها را برمی‌گرداند؛ بنابراین دادهٔ لازم برای نمایش/چاپ مجدد در دسترس است.
- فرم خرید/فروش فعلی یک فرم عمومی است؛ صفحهٔ فروش بیشتر فهرست اسناد است و گردش اختصاصی POS ندارد.
- خروجی PDF موجود برای گزارش‌هاست؛ مسیر مستقل فاکتور و چاپ فیزیکی فاکتور هنوز وجود ندارد.
- نام خریدار از قبل متنی و اختیاری است؛ برای این تصمیم مهاجرت دیتابیس لازم نیست، مگر آنکه ممیزی بعدی نشان دهد فیلدی برای snapshot نمایش/فروش واقعاً کم است.

## معماری هدف
1. **Presentation (renderer):** منوی فروش‌محور، صفحهٔ فروش سریع، سبد کالا، فهرست فاکتورها، جزئیات/پیش‌نمایش فاکتور و انتخاب اندازهٔ چاپ.
2. **Preload:** فقط APIهای محدود و صریح برای خواندن سند و درخواست چاپ/خروجی PDF؛ هیچ دسترسی مستقیم renderer به Node یا فایل‌سیستم داده نمی‌شود.
3. **Main process:** اعتبارسنجی شناسه و وضعیت سند، خواندن مجدد سند قطعی از SQLite، ساخت HTML امن با escape داده‌ها، بازکردن print dialog یا ذخیره PDF از مسیر انتخاب‌شده توسط کاربر.
4. **SQLite:** منبع حقیقت اسناد قطعی و snapshotهای آن‌ها باقی می‌ماند. چاپ/بازچاپ هیچ تغییری در موجودی یا سند ایجاد نمی‌کند.

## قواعد قطعی فروش و فاکتور
- فقط سند فروش با وضعیت `finalized` قابل صدور/چاپ فاکتور قطعی است؛ پیش‌نویس با برچسب واضح پیش‌نویس نمایش داده می‌شود و نباید به‌عنوان فاکتور قطعی چاپ شود.
- دکمهٔ «صدور فاکتور» همان عملیات نهایی‌سازی سند موجود است؛ سند دوم یا گردش موجودی دوم ساخته نمی‌شود.
- پس از موفقیت نهایی‌سازی، شمارهٔ فاکتور پایدار همان شمارهٔ سند فروش است.
- نام خریدار، یادداشت، تاریخ، اقلام، مقدار، قیمت واحد، تخفیف، نرخ/مبلغ مالیات و جمع‌ها از snapshot سند خوانده می‌شوند.
- قیمت/نام فعلی کالا نباید اطلاعات فاکتور قطعی قدیمی را بازنویسی کند. اگر نام کالا در آینده تغییرپذیر باشد، پیش از چاپ باید بررسی شود که نام زمان فروش snapshot شده است؛ در صورت نبود snapshot، مرحلهٔ مدل داده باید آن را با migration سازگار اضافه کند.
- تمام مبالغ در DB ریال صحیح باقی می‌مانند؛ تبدیل به تومان فقط در نمایش و با برچسب صریح انجام می‌شود.
- مالیات فقط مطابق نرخ ذخیره‌شده در سند نمایش داده می‌شود؛ مقدار قانونی یا نرخ پیش‌فرض جدید فرض نمی‌شود.
- برگشت فروش، فاکتور اصلی را حذف یا بازنویسی نمی‌کند؛ برگشت به‌صورت سند مرتبط مستقل باقی می‌ماند.
- چاپ مجدد idempotent است: نه شمارهٔ جدید می‌سازد، نه موجودی را تغییر می‌دهد، نه سند را نهایی‌سازی دوباره می‌کند.

## مشخصات تجربهٔ کاربری
### ناوبری
- «فروش» اولین و برجسته‌ترین گزینهٔ ناوبری و مقصد آغازین برنامه می‌شود.
- زیرصفحه‌ها/عملیات مرتبط: «فروش جدید»، «فاکتورهای فروش»، «برگشت از فروش».
- خرید، کالاها، موجودی، گزارش‌ها، پشتیبان‌گیری و تنظیمات در گروه‌های بعدی باقی می‌مانند.
- نمای کلی به صفحهٔ فرعی/داشبورد مدیریتی تبدیل می‌شود و CTA اصلی آن «شروع فروش» است.

### صفحهٔ فروش سریع
- جست‌وجوی فوری کالا با کد یا نام و انتخاب نتیجه با صفحه‌کلید/ماوس.
- افزودن چندبارهٔ یک کالا باید ردیف موجود را افزایش دهد یا طبق رفتار نهایی UX ردیف جدا ایجاد کند؛ این رفتار باید در آزمون UI تثبیت شود.
- سبد شامل کالا، واحد، مقدار، قیمت واحد، تخفیف، مالیات و جمع ردیف است.
- تغییر مقدار/قیمت/تخفیف، جمع‌ها را با منطق محاسبات صحیح فعلی به‌روزرسانی می‌کند؛ محاسبهٔ پول در renderer مرجع نهایی نیست و سمت main دوباره اعتبارسنجی می‌شود.
- خریدار و یادداشت اختیاری هستند.
- هشدار موجودی ناکافی مطابق قاعدهٔ موجود نمایش داده می‌شود؛ فروش بیش از موجودی مجاز است.
- اقدامات: ذخیرهٔ پیش‌نویس، صدور فاکتور، انصراف. صدور شامل تأیید خلاصه و هشدار موجودی در صورت نیاز است.

### فهرست و جزئیات فاکتورها
- فیلتر سریع بر اساس شماره، نام خریدار و بازهٔ تاریخ.
- نمایش شماره، تاریخ، خریدار (یا «مشتری حضوری»/«بدون نام»)، تعداد اقلام، مبلغ و وضعیت.
- اقدامات فاکتور قطعی: مشاهده، چاپ A4، چاپ حرارتی، ذخیره PDF، چاپ مجدد.
- اقدام‌های پیش‌نویس: ادامهٔ ویرایش یا حذف طبق قواعد فعلی؛ گزینه‌های چاپ قطعی غیرفعال.
- سند باطل‌شده باید با وضعیت ابطال و بدون القای اعتبار فاکتور نشان داده شود؛ سیاست چاپ نسخهٔ باطل‌شده با مهر/واترمارک در مرحلهٔ پیاده‌سازی تعیین و آزموده می‌شود.

## قرارداد چاپ
- یک مدل داده و یک مولد HTML مشترک برای هر دو اندازه استفاده شود؛ فقط stylesheet و تنظیمات صفحه تغییر کند.
- A4: سربرگ فروشگاه، شماره و تاریخ، خریدار اختیاری، جدول کامل اقلام، تخفیف/مالیات، جمع نهایی، یادداشت و محل امضا.
- حرارتی ۸۰mm: عرض ثابت ۸۰ میلی‌متر، چیدمان ستونی/فشرده، اقلام و جمع‌ها خوانا، حذف تزئینات غیرضروری.
- انتخاب مقصد چاپ/چاپگر توسط پنجرهٔ استاندارد ویندوز/Electron انجام شود؛ چاپ silent یا انتخاب خودکار چاپگر بدون درخواست کاربر مجاز نیست.
- PDF از همان HTML و با اندازهٔ انتخاب‌شده ساخته می‌شود؛ برای حرارتی، PDF باریک با عرض ۸۰mm تولید می‌شود.
- داده‌های درج‌شده در HTML باید escape شوند؛ هیچ HTML خامی از نام کالا، خریدار یا یادداشت پذیرفته نشود.
- پنجرهٔ چاپ باید با تنظیمات امن (بدون Node integration، context isolation و sandbox) ساخته و پس از پایان/خطا بسته شود.
- مسیر فایل PDF فقط از طریق save dialog انتخاب می‌شود؛ مسیر دلخواه renderer پذیرفته نمی‌شود.

## مدل داده و مهاجرت
- در گام اول migration جدید ممنوع است مگر ممیزی اثبات کند دادهٔ snapshot لازم وجود ندارد.
- **نتیجهٔ ممیزی و اصلاح (2026-11-02):** migration `005_document_item_product_snapshots.sql` سه ستون snapshot کد/نام/واحد را به `document_items` اضافه می‌کند و داده‌های قبلی را از `products` backfill می‌کند. `documents:get` اکنون snapshot را مقدم می‌داند و فقط در صورت NULL به مشخصات جاری fallback می‌کند. هنگام ذخیره/ویرایش پیش‌نویس، مشخصات همان لحظه در ردیف سند ذخیره می‌شوند. trigger پایگاه داده تغییر snapshot را پس از خروج سند از وضعیت draft مسدود می‌کند.
- migration 005 این ستون‌ها را اضافه و داده‌های قبلی را backfill می‌کند؛ دیگر migration دیگری برای این snapshot لازم نیست.
- `documents:get` از snapshot استفاده می‌کند؛ fallback فقط برای داده‌های NULL به‌عنوان مسیر سازگاری باقی مانده است.
- مشخصات فروشگاه برای سربرگ (نام/نشانی/تلفن/شناسه/لوگو) در این فاز می‌تواند تنظیمات اختیاری باشد؛ تا زمان تکمیل تنظیمات، نام Market و فیلدهای خالی/حذف‌شده نمایش داده شود. اطلاعات ساختگی درج نشود.
- شمارهٔ سند فعلی حفظ می‌شود؛ جدول شماره‌گذاری جدید یا شمارهٔ مستقل فاکتور ایجاد نشود.
